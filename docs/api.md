# REST API

`src/bms/api/app.py`, a thin transport layer over `main.run_pipeline`
(behavior engine) and `src.bms.digital_twin` (twin state). See
`docs/digital_twin.md` for why those two are separate modules and what the
digital twin actually tracks.

## Running it

```bash
pip install -r requirements.txt
uvicorn src.bms.api.app:app --reload
# or: make api
```

Interactive docs (auto-generated by FastAPI from the same code, so they
can't drift from this file the way hand-written docs can):
`http://127.0.0.1:8000/docs`

## What this is not

There's no persistent database, no auth, and no live telemetry ingest —
`/pipeline/simulate` generates a fresh simulated fleet and runs it through
the pipeline; it doesn't accept streamed BMS data yet. State lives only
for the lifetime of the process (see `src/bms/api/store.py`). This is a
demonstration/thesis-scope API, not a production deployment target — the
right next step for that would be a persistence layer and a real
ingestion endpoint, deliberately not built here since neither is needed
to demonstrate the architecture.

## Endpoints

### `GET /healthz`

Service liveness (not battery health — see `/batteries` for that).

```json
{"status": "ok", "n_runs": 2, "n_batteries_tracked": 20}
```

### `POST /pipeline/simulate`

Runs a simulated fleet through the full pipeline (ingestion → behavior
flags → risk → health → RUL → Guardian → digital twin) and folds the
result into the fleet store. Returns the state transitions this run
produced (a battery's first-ever evaluation counts as a transition, from
`null`).

Request body:

```json
{"n_batteries": 20, "rows_per_battery": 400, "seed": null}
```

`seed` is optional; omit it for a fresh random fleet each call, or set it
for a reproducible one (useful for demoing that re-running with an
unchanged fleet produces zero new transitions — see
`tests/test_api.py::test_repeated_identical_seeded_run_produces_no_new_transitions`).

### `GET /` and `GET /dashboard`

Serves the live fleet dashboard (`src/bms/dashboard/live_dashboard.html`) —
a single self-contained HTML/CSS/JS page with no build step and no
external CDN dependency. It's a browser client for the JSON endpoints
above: on load it calls `GET /batteries`, and clicking a battery calls
`GET /batteries/{id}` and `GET /batteries/{id}/timeline`. The "Run
Simulation" button calls `POST /pipeline/simulate`.

This is a different thing from the dashboard `main.py` generates
(`dashboard.html`, via `src/bms/dashboard/dashboard.py`): that one is a
static, no-server-required snapshot from a single CLI pipeline run — open
the file, nothing else needs to be running. This one is live — it needs
`uvicorn` running, shows twin state and transition history building up
across multiple `/pipeline/simulate` calls, and re-fetches from the API
rather than being baked at generation time. Use the static one for a
quick one-off report; use this one to see the digital twin actually
behave over repeated runs.

### `GET /batteries`

Current twin state for every battery the store has seen so far. Empty
until at least one `/pipeline/simulate` call has been made.

### `GET /batteries/{battery_id}`

Full detail for one battery: twin snapshot, Guardian's plain-language
report, risk level/score, the complete transition history for that
battery across all runs, and `evidence_confidence`/`evidence_note`. 404
if the battery isn't in the store.

`evidence_confidence` is one of `VALIDATED` / `HEURISTIC` / `MIXED` /
`N/A` — whether the causes Guardian identified for this battery are
backed by the calibration work in `docs/final_report.md` Section 4, or
are still unconfirmed hand-picked thresholds. Only temperature exposure
is currently `VALIDATED` (real, cohort-controlled signal, coefficient
0.0038 Ah/°C — see `src/bms/guardian/guardian.py` for the exact citation).
Current-based causes (fast charging, deep discharge) and health_index
itself are `HEURISTIC` — Section 4 found the former doesn't transfer
across conditions and the latter has no significant relationship with
real fade rate at all. This doesn't change what Guardian detects or how
severity is classified; it changes what the system says about its own
certainty, which previously wasn't visible anywhere in the output.

### `GET /batteries/{battery_id}/timeline`

Per-cycle stress score, SOC, and temperature for one battery, from the
most recent pipeline run's telemetry — for plotting a health trajectory.
404 if the battery isn't in the store, or isn't present in the *most
recent* run specifically (a battery from an earlier run whose telemetry
has since been superseded still has a twin state and transition history,
but no timeline — see `FleetStore.get_timeline_source`).

## What the numbers mean (read before citing any of them)

Every score this API returns — `health_index`, `risk_score`, `rul_cycles`,
`failure_likelihood`, `guardian_report` — is the same rule-based heuristic
documented and stress-tested in `docs/final_report.md`, not a validated
predictive model. `docs/final_report.md` Section 4 documents specifically
which parts (temperature exposure) have real evidence behind them and
which don't (the current-based flags, the fitted regression's
out-of-sample performance). This API makes those numbers reachable over
HTTP; it does not change what they're worth.

## Testing

```bash
python -m pytest tests/test_api.py -v
```

Tests use a fresh `FleetStore` per test (via `monkeypatch`), not the
running service's module-level store — see the fixture in
`tests/test_api.py` if extending this file.
